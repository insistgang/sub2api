# Plus 额度恢复后解除旧限流

## 问题与行为

上游提前重置额度后，两个 Plus 账号的 5 小时和周窗口已经恢复，但 Sub2API 仍保留重置前的
`rate_limited_at` / `rate_limit_reset_at`。账号列表显示“0% 已用”和“限流中”，调度器也会
继续排除这两个账号，直到旧截止时间到达。

问题不只是浏览器缓存。普通用量探针和自动额度检查原来只更新 `extra` 的用量快照；
调度缓存虽然同步了账号，数据库中旧的限流字段仍然存在。应用内消耗重置次数的流程原本
就有恢复逻辑，本次修复针对额度已在上游恢复、随后被重新查询到的情形。

`workbuddy-v0.2.18.3` 包含以下修正：

- 普通用量探针收到成功 HTTP 响应、完整且健康的标准 5 小时/7 天窗口后，清除请求发出前
  观察到的那一代旧限流。自动额度检查对新鲜的 `allowed=true`、`limit_reached=false`
  响应执行同样的校验与恢复。
- 数据库同时比较限流开始与截止时间，再执行条件更新；随后发送账号变化事件并刷新调度
  快照。并发产生的新 429，即使截止时间相同或更早，也不会被旧请求的结果覆盖。
- 保留模型级限流、过载、临时不可调度、人工调度开关和优先级；不恢复影子账号的母账号。
- 429/401 响应、缺失字段、无效百分比、未知窗口或已耗尽窗口不触发恢复。JSON 中缺少
  `used_percent` 不会因默认值为零而被误判为恢复。
- 网站取得用量后，对仍显示限流的普通 OpenAI OAuth 行重新读取服务器账号状态，再更新
  状态标记；不根据页面上的 0% 自行假定账号可用，也不应用旧版本的延迟响应。

只识别完整、明确的标准 5 小时/7 天窗口。其他合法但未识别的窗口格式继续展示，不自动
清除限流。没有新增数据库迁移，也不会为了修复状态消耗重置次数或启用额外积分付费。

## 验证

- 先复现“健康额度查询后旧限流仍在”，再通过新增服务回归；覆盖异常/部分响应、影子账号、
  独立状态保留与并发重新限流。
- 相关服务竞态检测、管理员重置/刷新测试以及仓库 SQL 条件更新测试通过。
- PostgreSQL 15 真库验证 7 个子场景通过。测试使用新建的隔离数据库，保留原测试断言和
  数据库迁移；私有 Go overlay 仅替换 Docker 启动步骤。测试数据库已删除。
- 前端相关组件 93 项、仓库关键前端测试 575 项通过；两组有重合。生产前端构建和改动文件
  ESLint 检查通过。
- 后端全包单测首轮只有 `internal/service` 包出现失败，原断言输出被截断；同代码、相同
  并发设置完整复跑该包通过，其余包首轮通过。不能把首次未复现失败归为已证实的基线问题。
  后续完整 JSON 日志已保留在私有证据目录。
- 实际生产故障期间，上游对两个账号均返回允许请求、两个窗口 0% 已用。备份后按原限流
  时间戳执行条件恢复，网站两行均恢复正常；新会话 Responses 请求与另一账号的定向
  GPT-6-Astra 测试均成功。

机器专属证据和操作记录位于维护者的 `~/.local/share/sub2api-dev/2026-10-25/plus-reset/`，
不包含在公开仓库中。服务器切换前须验证候选镜像、当前数据的隔离恢复与旧镜像回退，
仅替换应用镜像，保留 PostgreSQL、Redis、代理、账号、密钥、分组和持久化配置。

## 后续使用

如果额度在上游提前恢复，账号用量的下一次有效探测会校正旧状态；网站的“查询”可主动
触发一次探测。若上游仍限流、返回不完整窗口或查询失败，系统保留原限制，继续显示上游
实际结果。不要仅凭缓存的 0% 手动批量清空全部账号的限流状态。
